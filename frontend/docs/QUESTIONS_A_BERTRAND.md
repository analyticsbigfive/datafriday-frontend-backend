# Questions à Bertrand — tracker de clarification

> On n'a pas de base de code auto-porteuse : la compréhension fonctionnelle réelle passe par
> Bertrand (review, test, validation). Ce fichier évite que chacun tranche seul dans son coin une
> incompréhension du code ou d'une fonctionnalité — ce qui est la source la plus fréquente de bugs
> et de conflits sur ce projet (voir [`docs/bugs/00_INDEX.md`](bugs/00_INDEX.md), plusieurs bugs
> viennent de deux devs ayant chacun implémenté sa propre interprétation de la même règle — ex.
> le gating Team, [BUG côté front](bugs/) vs comportement attendu).

## Comment l'utiliser

0. **Bertrand est Product Owner, pas architecte.** Ce fichier n'est PAS une liste générale
   d'incertitudes techniques — c'est le canal pour les **règles métier / décisions produit** que
   seul Bertrand peut trancher. Avant d'ajouter une ligne, se demander : *est-ce que le code, la
   base, ou une convention déjà établie ailleurs dans le repo répond déjà à cette question ?* Si
   oui → ce n'est pas une question, c'est une vérification à faire (voir `docs/bugs/`,
   `docs/modules/`, ou lire le code directement). Est-ce que c'est un choix d'architecture, de
   schéma, de performance, ou de refactor ? → c'est une décision **technique**, elle revient à
   Ulrich (lead), pas à Bertrand — la tracer dans
   [`DECISIONS_TECHNIQUES.md`](DECISIONS_TECHNIQUES.md) ou directement dans la fiche
   bug/module concernée, pas ici. Seule reste ici une question qui est *authentiquement* de la
   règle métier/produit, sans réponse possible en lisant le code ou la donnée.
1. Bloqué sur une incompréhension **produit** (règle métier, comportement attendu, arbitrage entre
   deux usages) qui ne se résout ni par le code ni par la donnée → ajouter une ligne ci-dessous,
   statut 🔴.
2. Poser la question à Bertrand.
3. Une fois répondu : mettre à jour la doc canonique concernée (page de module dans
   [`docs/modules/`](modules/00_INDEX.md), [`docs/adr/`](adr/00_INDEX.md), ou
   [`docs/bugs/`](bugs/00_INDEX.md) si la réponse révèle un bug) — **et le code si la réponse
   implique un renommage/commentaire/refactor** — puis lier la mise à jour ici et passer le
   statut à 🟢.
4. **Ne jamais merger un code qui repose sur une hypothèse encore marquée 🔴.**

Même mécanique pour une fonctionnalité neuve : confronter le cahier des charges au code existant,
lister ici ce qui reste ambigu **au niveau produit**, trancher avec Bertrand avant d'écrire le code
définitif.
