Vue d'ensemble

SaaS de gestion F&B (restauration) dans les grands lieux : stades, arénas, salles d'événements. Répond à : « Combien vais-je vendre, combien commander, combien de staff, et combien ai-je gagné ? »

👤 Utilisateur

Opérateur F&B / traiteur de stade gérant plusieurs points de vente sur plusieurs étages, pour des dizaines d'événements/an.

🎯 Valeur

Prévoir les ventes → commander le bon stock → éviter rupture et surstock → mesurer la performance réelle.

📐 Métrique reine

Per-capita = revenu ÷ spectateurs. Compare un match 20k à un concert 40k sur la même base.
Deux bases de code dans ce repo :
  • Vue 3 (src/) = app production réelle. vue-router + auth multi-org + Vuex + backend REST. C'est l'app vivante.
  • React (versionReact/) = export Figma Make, un seul App.tsx (3029 l.), sans auth ni router, backend Supabase Edge Function + KV store. = maquette de référence UI/UX + logique métier d'origine qu'on porte vers Vue.
Boucle de valeur 
Prédire → Commander stock → Vendre pendant event
   → Compter (Inventory) → Réarmer (Restock) → Mesurer (Analyse) → ↺ améliore la prédiction

Backend auth = Supabase. Le token JWT porte un claim custom tenant_id (= organisation) injecté par un hook Supabase.

Inscription

Connexion

/login → signIn() → setAccessToken() → checkOnboardingStatus() → org ? /dashboard : /onboarding

Mot de passe oublié

/forgot-password → email → /reset-password → /login

Démo / test

?demo=1 court-circuite l'auth. Banc moteur : /predict-test (mock JSON, sans auth).
🔑 Piège n°1 (silencieux) — Après createOrganization() / joinOrganization(), il faut refresh la session Supabase (auth.js L.261-274). Sinon le JWT ne contient pas encore tenant_id → tout appel API suivant (ex. GET /spaces) renvoie 401. Aucun message clair, juste un 401.

Flux token : token gardé en mémoire (client.js). Si absent (reload, deep-link, OAuth), l'intercepteur le récupère depuis la session Supabase — sauf si _explicitlyLoggedOut=true (posé par signOut() qui efface le token avant le logout Supabase). Sur 401 l'intercepteur tente un refresh, sinon redirige /login.

Coût & marge

component.cost = Σ(ingredient.costPerRecipeUnit × numberOfUnits) menuItem.cost = Σ(component costs) marge % = (sellingPrice − cost) / sellingPrice × 100
Coût figé à la création — changer un prix marché ne recalcule pas automatiquement les menu items qui l'utilisent. Bouton « Refresh Costs » (POST /menu-items/refresh-costs) requis.

9 · Restock / Réarmement

Après comptage, recalcule le réapprovisionnement. /spaces/:id/restock

restockQty = max(0, targetQuantity − remainingQuantity)

Pipeline (stockPlanning.js) : pour chaque event sélectionné → prédictions → buildStockRequirements() → ajustement % (slider 0–200) → mode packaging (« 5 boîtes de 10 » vs « 50 pcs ») → soustrait le remainingQuantity de l'inventaire précédent.

« Remaining » = snapshot de l'event précédent, pas le comptage en cours. Si l'inventaire précédent n'a pas été sauvé → remaining = 0. Expansion récursive des combos plafonnée à 10 niveaux, pas de détection de cycle.

Moteur Predict — l'algorithme

src/utils/predictiveAnalytics.js (origine : versionReact/.../predictiveAnalytics.ts)

But : prédire les ventes par (shop, menuItem) pour un event futur, à partir d'events passés similaires pondérés.

Phase 1 — Scorer les events passés

Filtres durs (exclusion immédiate → null)

  • Type d'event différent (si les deux connus)
  • Catégorie différente
  • Affluence hors ±40 % : pTickets < 0.6×tTickets || > 1.4×tTickets
  • Show time > 3 h d'écart

Score souple (points additionnés)

CritèrePoints
subcategory exacte800
équipe visiteuse (sport) exacte800
performer (concert) exact800
sponsor (MICE) exact400
jour de semaine : même jour500 · (250 si même groupe weekend/semaine)
show time : exact / ≤60min / ≤120min400 / 300 / 100
affluence proche (proportionnel)0–200
type + catégorie (déjà filtre dur)100 + 100
scalingFactor = targetTickets / pastTickets

Phase 2 — Sélection & pondération

  • Garder les 10 meilleurs scores
  • Aucun match → fallback : 3 events passés au hasard, isLowConfidence=true, confiance=0
  • weight[i] = score[i] / Σ(scores)

Phase 3 — Agrégation par item

Pour chaque (shop, menuItemId) :

qtySum = Σ( past_quantity × scalingFactor × weight ) revSum = Σ( past_revenue × scalingFactor × weight )
Normalisation « sparsité » — si un item n'apparaît que dans K des N events sélectionnés, on divise par weightCovered (somme des poids des events qui ont l'item). Sans ça, les items absents de certains events seraient sous-estimés. Ordre des opérations : scaling AVANT weight.

Timeline (usePredictiveTimeline) : poids appliqués à la volée value × eventWeight × (predictedAttendees/pastAttendees), puis agrégé par (minute, shopId, menuItemId).

Banc de test /predict-test : montre la table des events scorés (score/maxScore %, poids, scaling, exclusions + raison) et la trace de calcul par item.

Formules Analyse

src/composables/useMetricsCalculator.js

Entrées : filteredShopGranularData (lignes de vente), chartFilteredEvents, menuItemCostMap.

revenue = Σ record.revenue cost = Σ costMap[record.menuItemId] × record.quantity transactions = Σ record.transactionCount ticketsScanned= Σ (event.ticketsScanned || event.attendees) avgRevenuePerEvent = revenue / eventsWithRevenueCount avgPerTransaction = revenue / transactions ← « panier moyen » perCapita = revenue / ticketsScanned ← métrique reine margin % = (revenue − cost) / revenue × 100 transactionRate = transactions / operatingMinutes (défaut 180 min/event)

Backend KV (version React)

versionReact/src/app/supabase/functions/server/index.tsx (12 723 l., Deno + Hono)

⚠️ C'est le backend de la maquette React, pas celui de l'app Vue (REST /api/v1). Mais il documente la logique métier d'origine que l'API Vue reproduit.

Stockage = Key-Value

Table Postgres kv_store_eb31619c (key TEXT, value JSONB). Tout est rangé par préfixe de clé :

space:config:event:event-type:event-revenue: menu-item:menu-component:ingredient:market-price:packaging: category:type:category-agg:type-agg: shop-element-mapping:menu-item-mapping:location-space-mapping: shop-granular-records:shop-event-revenue:supplier:team:sponsor:

Logique métier à connaître

  • Event revenue : lit fnb_sales_raw (pagination 1000/chunk), groupe par Long_ID (= une transaction client) et somme Total_HT. Format euro à virgule géré.
  • Aggregations : pré-calcule coût/prix/marge par catégorie & type (cher : joint tous les menu items) → caché en KV avec dirty-tracking.
  • Aggregation queue : à chaque save de menu item → marque catégorie+type « dirty » → traité par lots (10 items, timeout 20s) au prochain appel. Évite de bloquer les saves.
  • Shop performance : job background multi-phases avec checkpoints (resumable, timeout 10 min) → calcule transaction-rate par shop depuis la timeline.
  • Transaction distribution : % de transactions par type d'item (60% Beverage / 40% Food…).
Mappings doubles — ancien (consolidé shop-mappings:{spaceId}) vs nouveau (granulaire shop-element-mapping:). Les routes lisent le nouveau ; des migrations convertissent. Vérifier lequel est actif. Aussi : dates DD/MM/YYYY (saisie) vs YYYY-MM-DD (DB) → un mismatch = résultats vides.

IDs temporaires temp-* → UUID au save. depth ≠ height (depth = Y en 2D). Sous-types = tableaux. Réactivité Vue : réassigner la référence du tableau de floors.

Menu F&B

Coût figé à la création — pas de cascade quand un prix marché change (bouton refresh-costs). Expansion combo plafond 10 niveaux, pas de détection de cycle. Items « packaging » silencieusement ignorés à l'expansion (si « pack » dans le nom → drop accidentel).

Predict

Ordre scaling × weight (pas l'inverse). Normalisation sparsité sinon sous-estimation. Filtres durs excluent avant tout scoring (impossible de rattraper par le poids). Low-confidence = 3 events au hasard.

Analyse

Canvas remount trap — la key de EventTimelineChart ne change que sur eventId/longueur de liste, sinon crash ResizeObserver « ownerDocument ». Timeline synthétique si pas de données (gaussienne 180 min). Variations toujours via getters store, jamais en local.

Inventory / Restock

Double persistence LS + API ; changer d'event en plein comptage perd l'état non sauvé. « Remaining » = event précédent (0 si pas sauvé). Tabs shop/storage partagent le state de filtre mais logique différente.
